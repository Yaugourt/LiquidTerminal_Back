## 1. Policy (agreed 2026-10-13)

- **Live data first.** Live data, and never blocking a visitor, beat upstream savings.
- **HypeDexer limits are high.** Credits are a cost to watch (§4.2, the daily meter at `src/utils/hypedexer-credit-meter.ts:25`), not a reason to slow a live widget.
- **Thousands of users expected.** Scale through shared backend caches, single-flight and stale-while-revalidate (the `:last` copy, §3 "Shared machinery"), so upstream cost stays flat in the number of visitors.
- **No per-visitor caps as a scaling tool.** Per-IP limiters (§3.3) stop abuse; they are not how load is kept in check.
- **Hard upstream limits still hold:** Hyperliquid 1,200 weight/min per backend outbound IP (`src/core/base.api.service.ts:162-167`, §4.1); Hyperfolio's per-second burst limit (`src/clients/hyperfolio/hyperfolio.client.ts:47-59`) and its unknown paid quota (§4.3).

**How to change a number.** Edit the code and this file in the same commit. Both repos keep an identical copy (`docs/DATA_BUDGET.md`), so update both. Then recheck section 4: the Hyperliquid margin (§4.1) and the HypeDexer daily total (§4.2).

## 5. Front

Paths are front-relative (`src/…`); backend paths carry `back:` and backend rows are cross-referenced by their ID from §3 (BK-P pollers, BK-R routes, BK-S sockets, BK-L limits).

How to read the tables:

- **Cadence** is the front poll period P. Every poll goes through `useDataFetching` (or `setVisibleInterval`), so it pauses in a hidden tab (§5.3). "once" = fetched on mount only (`refreshInterval: 0`); "push" = websocket.
- **Backend** is what bounds the age of the answer the backend hands out: the cache TTL of the key, or the poller interval that writes it. Two numbers joined by "+" are two cache layers stacked (service key over client key).
- **Worst** is the worst-case age of what the visitor sees = P + backend age. It ignores upstream lag (Hypurrscan regenerates its files, HypeDexer indexes with a delay) and the ≤ 1.5 s a reader waits for a live key's refresh (`back:src/core/cache.service.ts:86`). A live key (TTL ≤ 30 s, `cache.service.ts:78`) whose refresh is slow can serve its last copy for up to 4 TTLs, at least 60 s (`:87-88`): that is the outage case, not the normal one. Browser-direct calls: Worst = P. A poll may also take a sibling widget's cached answer up to P/2 old (§5.3), so a key that two widgets of one page share can read up to P/2 older than shown.
- **Hidden**: `P` = polls skip while hidden, one catch-up poll on return (`src/lib/visibility.ts:21-56`); `S60` = socket closed after 60 s hidden, reopened and resubscribed on return (`src/lib/websocket-client.ts:38`); `ON` = socket stays open in a background tab; `—` = nothing recurring.

**Request policy and GET cache** (`src/services/api/http/request-policy.ts`, `src/services/api/cache/cache.service.ts`): every GET through `get()` is cached in memory per tab, keyed by method + URL + params + body (`cache.service.ts:26-30`), for 30 s at most (`:8`), 100 entries (`:9`, cleanup from 80, at most once a minute, `:10`, `:21`). The policy reaches only requests started synchronously by the fetchFn (`request-policy.ts:1-15`). Consequence for Worst: two widgets on the same key can add up to P/2 to FR rows when one reuses the other's answer.
